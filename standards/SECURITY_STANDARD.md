# 共通セキュリティ標準 v1.0

## 1. 守るものと分類
新規開発または大きな変更に先立ち、`templates/PROJECT_PROFILE.md` の情報を調査する。機密性・完全性・可用性、患者安全、停止影響、公開範囲、第三者連携を評価しA/B/Cに分類。リスクは `RISK_REGISTER.csv` に記録する。可能性×影響度（1〜5）は**簡易優先度**に過ぎない。患者安全・法律・重大な漏洩は点数にかかわらずエスカレーションする。

## 2. リスク処置
各リスクに「回避・低減・共有/移転・受容」、オーナー、期限、残余リスク、確認証拠を割り当てる。AIはリスク受容を承認できない。重大な未解決リスクがある場合、本番公開非推奨と報告する。

## 3. 最低限の設計原則
- 最小権限。認証だけでなく**API/サーバー側**で認可を行い、直接URL/API呼び出しでも検証する。
- パスワードは平文保存しない。適切な認証実装を用い、セッション・再認証・ログアウトも設計する。
- SQLはパラメータ化。HTML出力時の適切なエンコーディング。CSRF/XSS/ファイルアップロード/OSコマンド等は該当機能に合わせて検査する。
- シークレットをコード、Git履歴、ログ、AIへのプロンプトに置かない。露出時は削除だけでなく失効・再発行する。
- 構造化監査ログ（誰・何・いつ・結果・対象ID）と運用/エラーログを分離。ログにも個人情報を極力含めず、権限・保持期間・改ざん耐性を設計。
- 保存データの定期バックアップ、別系統の保存先、復元手順、復元**実地試験**を用意。バックアップ頻度は許容データ損失（RPO）と復旧時間（RTO）で決定。
- 入力誤り・競合更新・二重送信・通信/DB障害・停電等の異常系で安全な失敗処理を行う。患者安全に関係する場合は業務の代替運用も定義。
- Gitによるコード履歴、検証済みリリース識別子、DBスキーマ移行と巻き戻し可能性を文書化する。
- 依存関係更新・脆弱性情報を継続監視する。Dependabotが扱えないNode本体・WordPress本体・OS等は別途管理する。

## 4. 参照基準の適用
- NIST CSF 2.0：組織のガバナンス・識別・保護・検知・対応・復旧。
- NIST SP 800-218 SSDF：開発組織と開発ライフサイクルの実践。
- IPA「安全なウェブサイトの作り方」：日本語の具体的実装・脆弱性例。
- OWASP ASVS 5.0.0（安定版）：該当Webアプリの具体的な検証要求。初期は適用性を判断し、個別要件を選定する。
- 医療情報を扱う場合：厚労省「医療情報システムの安全管理に関するガイドライン」第7.0版（2026年6月）および関係法令・最新Q&Aを確認。
要求事項IDを捏造しない。公式原本を確認できない場合は「未照合」と記録。基準の版・URL・該当項目・実装・テストを `VERIFICATION_MATRIX.csv` に紐づける。「NIST準拠」など包括的な主張はしない。

## 5. 開発工程とゲート
1. **調査**: 既存構成、機能、データフロー、信頼境界、依存関係、バックアップ、アクセス権、運用担当を確認。
2. **計画**: 変更による危険、影響範囲、テスト対象、戻し方を提示。
3. **実装**: 小さな変更単位で実装。関連するテストを用意。必要な安全機能を勝手に弱めない。
4. **自動検証**: 単体/結合/回帰/権限の否定系、依存脆弱性、シークレット漏洩、可能ならSAST、該当時DAST。テストが未存在なら成功を主張せず不足を報告。
5. **独立確認**: CIの実行結果とテスト設計をレビュー。高リスクでは人間の手動検証または専門家チェック。作成者AIと別AIによるレビューは補助であり独立保証ではない。
6. **公開判定**: `RELEASE_CHECKLIST.md` に結果と証拠を記録。重大な未解決問題/無検証の患者影響変更があれば公開停止を推奨。
7. **運用**: ログ・バックアップ成功状況、脆弱性情報、権限、インシデントを定期確認。

## 6. AIへの厳格な禁止・報告義務
- 承認なく本番デプロイ、本番DB操作、秘密情報の読み取り/外部転送、保護設定の無効化、検証パイプライン削除を実施しない。
- 患者情報・実業務の秘密情報を、外部AI・外部テストサービス・開発環境へ転送しない。
- テストが失敗したら隠さない。テストそのものを書き換えて失敗を消さない。仕様変更が必要なら理由と承認が必要。
- 「実装済み」「テスト成功」「未実行」「手動確認待ち」を厳密に区別。コマンド、終了コード、実行日時・環境、コミット、証拠パスを記録し、秘密情報はマスキングする。
- 本番リリースの最終承認者は人間。GitHubのブランチ保護、CI必須チェック、Secrets権限、本番資格情報の分離は実装によって強制する。

## 7. AIのタスク終了時の報告フォーマット
- 変更概要 / ファイル / 変更の理由
- リスク変化（追加・低減・残余）
- テスト一覧：コマンド・結果・証跡・未実行理由
- 該当基準と確認済み要件（原典・版）
- 秘密情報/患者情報への影響
- ロールバック/復旧手順
- 公開判定案：準備完了候補 / 条件付き / 公開非推奨（最終承認ではない）
